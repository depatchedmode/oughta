# Swift

What the core skill's categories look like in Swift and on Apple platforms, and which tools find them. Read it once, then use it to guide investigation. The patterns below are candidates, not automatic defects; establish their responsibility and consumers before changing them.

## Commands

Fallbacks for when the project's Makefile, CI workflow or agent instructions don't say. Find out first whether the project is a SwiftPM package, an Xcode project or workspace, or packages inside a workspace.

| Need | SwiftPM | Xcode |
| --- | --- | --- |
| Fast check | `swift build --build-tests` | `xcodebuild build-for-testing -scheme <S> -destination 'platform=iOS Simulator,id=<UDID>' -quiet` |
| Full suite | `swift test` | `xcodebuild test-without-building -scheme <S> -destination 'platform=iOS Simulator,id=<UDID>' -quiet` |
| Lint | `swiftlint`, if `.swiftlint.yml` exists | same |
| Format | `swiftformat --lint .` to check and `swiftformat .` to fix, or `swift-format`, whichever the project configures | same |
| Dead code | `periphery scan`, or SwiftLint's analyzer rules; both need setup, see below | same |
| Target graph | `swift package describe --type json`, reading each target's `target_dependencies` | target dependencies in `project.pbxproj` |

Discovery: `xcodebuild -list -json` gives the schemes. Use the host's device tools to discover and reserve a simulator; pass its UDID as `id=` because names can repeat across runtimes. Pass `-project` or `-workspace` when needed. Use `platform=macOS` for Mac targets. Preserve signing and entitlement requirements; a signing bypass is not verification of behavior that depends on them.

`swift build` and `swift test` build for the macOS host, so they fail for an iOS-only package that imports UIKit. For those, discover the package's actual scheme with `xcodebuild -list -json`, build that scheme for `generic/platform=iOS Simulator`, and test it on a simulator UDID. Do not assume a generated scheme name.

Dead code: `periphery scan` needs `--setup` once, or a `.periphery.yml` naming the schemes, and `--retain-public`, or it reports package and FFI API as dead. SwiftLint's `unused_declaration` and `unused_import` must be listed under `analyzer_rules` in `.swiftlint.yml`, and `swiftlint analyze --compiler-log-path <log>` needs the log of a clean `xcodebuild` build, which costs a full rebuild. Run either once at step 0, not per fix.

Batch related fixes per build when necessary. Run focused lifecycle/UI tests at the checkpoint where their behavior changes, then the full affected suites at final integration. Do not defer all platform evidence to the end merely because it is slower. If piping output through a formatter, preserve the build command's exit status. For XcodeGen or Tuist projects, regenerate the project after file additions or moves.

Isolate simulator and DerivedData ownership or run competing checks sequentially. Record interrupted runs and rerun under controlled conditions. A macOS package result does not establish iOS behavior; record platform-specific baseline failures separately. Rebuild native libraries and bindings before consumer runtime tests.

Skeleton:

```sh
rg -n '^\s*(@\w+\s+)*(public |open |internal |private |fileprivate |package )?(final |static |class |override |mutating |indirect )*(class|struct|enum|protocol|extension|actor|func|init)\b' --type swift
```

## Can files move?

- Synchronized folders, `PBXFileSystemSynchronizedRootGroup` entries in the pbxproj, arrived in Xcode 16. Files inside one move without a pbxproj edit, unless they're listed in an exception set's `membershipExceptions`. A move between folders synced to different targets changes the file's module.
- Classic groups, `PBXGroup` and `PBXFileReference` entries, reference every file by path. A move on disk breaks the build until the project file is updated. Edit the pbxproj with care, or don't move. Xcode 16 projects mix both kinds, so check the folder you're moving within.
- Projects generated by XcodeGen or Tuist: edit `project.yml` or `Project.swift`, never the pbxproj, then regenerate.
- SwiftPM: files under `Sources/<Target>` are picked up automatically. Moving a file between targets changes a module boundary and every `import` of it.

## Generated and vendored code

Do not hand-edit generated output; change its source and regenerate. Configuration and lockfiles still belong in dependency and compatibility analysis even though they are not application code.

- uniffi bindings: `<Crate>.swift`, `<Crate>FFI.h`, `<Crate>FFI.modulemap`, and a generated `Package.swift` that wraps an XCFramework.
- SwiftProtobuf `*.pb.swift`. SwiftGen output such as `Assets.swift` and `Strings.swift`. R.swift's `R.generated.swift`. Sourcery's `*.generated.swift`.
- Vendored or forked packages checked into the tree.
- `Package.resolved` isn't code. Xcode's asset symbols live in DerivedData, not the tree.

## Fixed boundaries

- `public` and `open` API of a package consumed by another app or repo.
- `@objc` and `@_cdecl` declarations other languages call, and anything an FFI header declares, when the consumer lives outside this repo. For coordinated in-repo consumers, regenerate bindings, rebuild the native library, and update callers in the same fix. Independently released consumers still require compatibility.
- `Codable` keys matching a wire format, and anything persisted: Core Data entity and attribute names need a migration to change, `UserDefaults` keys outlive the code, `NSKeyedArchiver` class names are in the archive.
- `@main`, the App Delegate and Scene Delegate, Info.plist keys and entitlements, URL schemes, and the separate targets extensions and widgets must live in. The platform decides these.

## Hidden links

- Anything coupled by a string: `Notification.Name("…")` posted in one place and observed in another, `UserDefaults` and `@AppStorage` keys, segue and storyboard identifiers, cell reuse identifiers, `NSLocalizedString` keys, KVO key paths, selectors, deep link paths.
- `.shared` singletons mutated in one module and read in another.
- Info.plist keys the code assumes and nothing checks.
- `#if DEBUG` paths that must mirror the release path by hand.
- A feature's model, view and tests in three trees.

## Needless links

- Review overly broad visibility within a module. Use `private` or `fileprivate` for implementation details, and a separate target only when a genuine module boundary is needed.
- Views that read a view model's internals, or that know the network layer exists.
- One `ObservableObject` passed as `@EnvironmentObject` to every view, so every view depends on everything.
- `AnyView` and other type erasure that hides which type a caller really depends on.
- A package target that imports the app's module.

## Surplus

- Dead code: `periphery scan`, or SwiftLint's `unused_declaration` and `unused_import` analyzer rules, set up as the Commands section says.
- `Manager` and `Service` classes that wrap one Apple API and add nothing.
- Protocols with one conformance and no demonstrated boundary or substitution role. One conformance alone does not make a protocol surplus.
- Coordinators that only forward.
- `#if` branches for platforms the project doesn't ship.

## Special cases

- Force unwrap `!`, `try!`, `as!`, and `fatalError` outside tests.
- `try?` that discards the error, and empty `catch` blocks.
- `DispatchQueue.main.asyncAfter`, `Task.sleep`, `usleep` and retry loops outside tests. The hundred-millisecond wait is the classic.
- `DispatchQueue.main.async` added to fix a threading bug instead of the design that caused it.
- `@unchecked Sendable`, `nonisolated(unsafe)`, `@preconcurrency`.
- `#if DEBUG`, `#if targetEnvironment(simulator)`, `#if os(…)` and `if #available` branches.
- Suppressions. Grep `swiftlint:disable`, `swiftformat:disable` and `periphery:ignore`, and read `disabled_rules` in `.swiftlint.yml`.
- `@objc` on something with one caller, unless a `#selector`, KVO or an Objective-C consumer needs it.
- `[weak self]`: inspect ownership, retain cycles, and closure lifetime before changing capture semantics. Retain justified weak captures.
- `XCTSkip`, and Swift Testing's `.disabled` trait.

For unchecked concurrency declarations, inspect every access to protected state and the synchronization invariant. Lock-backed state may legitimately require `@unchecked Sendable`; retain and explain it when supported by the design. Review actor isolation, ownership, and teardown rather than deleting the annotation mechanically.

## Comments mode

Keep:

- `///` doc comments on `public` and `open` declarations. Quick Help and DocC read them.
- `// swiftlint:`, `// swiftformat:` and `// swift-format-ignore` directives, `// periphery:ignore`, and `// sourcery:` annotations.
- `// MARK:` lines, unless the file is being split anyway.

## Tests mode

- `@testable import` is not a defect. Judge whether assertions protect behavior or incidental structure. Interaction ordering may itself be a lifecycle contract.
- XCUITest and anything else that needs a simulator or device: say whether you ran it.
- Snapshot tests can catch visual regressions. Understand their configured tolerance, platform, and fixtures before changing or removing them; do not refresh goldens merely to clear a failure.

Use controlled deadlines, completion signals, and lifecycle observations instead of fixed sleeps or repeated yields. A negative assertion needs proof queued work was processed. Ensure timeout/fail-fast tests fail within a bound and unblock their worker even after a failed assertion. Verify that teardown releases all owned observation/forwarding tasks. For a critical protection, selectively break it to confirm the test catches the intended regression, then restore and rerun.

## Graph and partition

Inside a module, files don't import each other, so imports miss internal dependencies. Use the package/Xcode target graph and type references inside each target. Text searches for declared names are a navigation aid, not a complete semantic graph; inspect extensions, generated code, selectors, and runtime string contracts as well.

Partition subagents by target, then by top-level folder inside the app target.

## Primary sources

Use the documentation matching the adopting project's pinned versions.

- [SwiftLint](https://github.com/realm/SwiftLint#analyze): analyzer configuration and compiler logs.
